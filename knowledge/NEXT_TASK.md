- **Patterns established across all sessions so far, expected to recur — don't re-litigate each time (but still flag+ask if a genuinely new situation comes up):**
  - If a new component is itself meant as a background/full-bleed element, its container pages likely need the same transparent-body treatment as FloatingLines got.
  - If a new component has pointer/hover/scroll interactivity and is used as a full-page backdrop, check first whether it listens on `window`/`document` directly (no bridge needed, e.g. `SplashCursor`, `LiquidEther`) or on its own element (needs the `dispatchEvent` bridge pattern in `main.jsx`, e.g. `FloatingLines`, or the `sentinelscan:scan-update` bridge feeding `ScanTerminal`) — never modify the shipped component file either way.
  - If a new component needs to coexist with something else that must never be interrupted (another persistent background, a global timer, a site-wide nav overlay), mount it on its own independent `createRoot()` rather than as a sibling in a shared tree — established pattern for every site-wide mount (background, splash cursor, intro, nav menu, dashboard terminal all do this).
  - If a target component turns out to be paywalled/gated (checked by hitting its registry JSON endpoint directly, e.g. `curl` — a `401`/`403`/license-key error means it's paid or auth-gated), stop and flag it to the user rather than assuming — hit repeatedly for 21st.dev URLs (session 6's `shadcnspace/social-icon`, session 7's `interactive-portfolio-terminal-component`), always resolved by asking the user to paste the source directly.
  - **If asked to replicate an existing ASCII-art/box-drawing banner's exact font for new text, don't hand-draw new glyphs** — identify the actual font (e.g. via `pyfiglet`, trying likely font names against the known text until it matches byte-for-byte) and regenerate programmatically. Session 7 hit this for the dashboard terminal's `TERMINALLY`→`SENTINEL SCAN` banner; a hand-drawn first attempt was explicitly rejected by the user.
  - **When extracting a shader/animation mechanism from a button-shaped component to apply to a non-button element (e.g. a hover-glow border on a panel), don't assume the button's exact trigger model (e.g. proximity radius) is what's wanted** — ask or default to literal hover (`pointerenter`/`pointerleave`) unless told otherwise. Session 7's `SpecularFrame` needed a correction for exactly this.
  - **A user-reported size/layout regression is not always a real code regression** — check `getComputedStyle`/`getBoundingClientRect` before assuming a fix requires undoing a recent change. Session 7: "the terminal shrank" turned out to mean "the page got shorter because a sibling card was removed," not an actual CSS change to the terminal itself — the fix was to grow the terminal to reclaim the space, not revert anything.
  - **A `max-width` increase on a page's shared content container (`<main>`) does not meaningfully widen one specific element inside it** if that element was already `w-full` within that container — the container itself is the bottleneck. To make one element genuinely wider than its siblings, give it its own "breakout" width independent of the shared container (e.g. `w-[90vw] max-w-[90vw] relative left-1/2 -translate-x-1/2`), not a bump to the container's own `max-w-*`. Session 7 tried the wrong approach first (bumping `<main>`'s `max-w-[1440px]`→`[1800px]`) and had to revert it.
  - **CSS conflicts between a shipped component and this site's existing global styles are a recurring category of bug.** Root-cause with `getBoundingClientRect()`/`getComputedStyle()`/`elementFromPoint()` via `javascript_tool` (subject to the Chrome approval gate below — ask first), never by guessing from the visual symptom. Fix via scoped CSS overrides (using the component's `className`/element selector as the scope hook) in either the react-app's own `index.css` or the site's `static/css/styles.css`, never by editing shipped component files. A stylesheet `!important` rule beats a plain (non-important) inline style set by a shipped component — useful when the component's own inline styles (not just its stylesheet) need overriding (session 7, `SplitText`'s `overflow: hidden`).
  - **This codebase runs two separate Tailwind engines simultaneously** — the sitewide Tailwind Play CDN (v3, JIT-scans the whole live DOM) and the react-app's own precompiled Tailwind v4 bundle. Both generate rules for any Tailwind class name appearing anywhere in the DOM, including inside React-rendered markup. For most utilities this is harmless (same computed value from either engine), but **v3 and v4 emit `transform: translate/scale/rotate(...)` vs. separate standalone `translate`/`scale`/`rotate` CSS properties respectively for the same class names** — since those are different properties, the browser *composes* them instead of one overriding the other, silently doubling the visual effect. Any future component using `-translate-*`, `scale-*`, or `rotate-*` utilities for positioning/sizing should be visually double-checked against its expected position. Fix pattern: scoped `transform: none !important` (or similar) targeting just that element, not a global Tailwind config change.
  - **A component sized/positioned in `em` units relative to its own font-size will silently break once that font-size is overridden smaller** — re-check every rule implicitly sized relative to a font-size you change (padding, absolute-position offsets, sibling gutters).
  - **`overflow-x-hidden` + `overflow-y-visible` does NOT give a genuinely visible y-axis** (the `visible` value gets silently promoted to `auto`, still clips). Use `overflow-x-clip` instead when one axis needs to stay genuinely visible. Verify with `getComputedStyle(el).overflowY`.
  - **When a user says "use it exactly as shipped," that means the animation/interaction *mechanics*, not necessarily every prop default, outer wrapper sizing, or scrap of demo scaffolding** — session 7's `ScanTerminal` dropped the original's `min-h-screen` full-page centering wrapper (wrong context for a component embedded in a page column) while keeping its window chrome/shader/animation verbatim, and this was accepted without objection. When a user says "don't copy the UI, just copy the animation" (session 6, Skiper106), that's an explicit instruction to hand-extract the mechanism into a hook/function rather than vendoring the file at all. If a fix requires editing a vendored file's *internals* rather than just how it's invoked/wrapped or what's extracted from it, that's a bigger step — flag it rather than silently forking without saying so.
  - **For "only when X" requests about a continuous physical quantity (speed, distance, time), default to a continuous scale/curve, not a binary on/off cutoff** — established session 5 (`SplashCursor` splat intensity), still the right default.
  - **Rotating/transformed elements positioned flush against a viewport edge on a page with height pinned to exactly `100vh` can cause scrollbar flicker** — Chrome counts a transformed descendant's visual overflow toward an ancestor's *scrollable* overflow even though transforms don't affect layout. Fix: a static (never-transformed) `overflow:hidden` wrapper sized past the element's worst-case rotated bounding box (a square of side `s` rotated about its center maxes out at `s*sqrt(2)` on the diagonal). Verify by polling `document.documentElement.scrollHeight` across a full animation cycle, not a single snapshot.
  - **When two sibling elements need to share a visual "bottom baseline" and one of them has invisible padding (e.g. a rotation-clipping box), align by shifting the padded element's box with a static offset (e.g. `margin-bottom`) — not by forcing both into equal-height centered boxes**, which instead pulls the *other* (unpadded) element away from the true edge.
  - **Small SVG icons (roughly under ~10px) whose path coordinates run close to their viewBox edge can get clipped by the SVG's own default `overflow:hidden`, purely from sub-pixel rounding** — the path itself never actually exceeds the viewBox. Fix: `overflow: visible` on the `svg` element, scoped via a parent class selector; costs nothing visually.
  - **An overlay panel that only covers part of the viewport (e.g. a slide-out menu at `clamp(260px, 38vw, 420px)` wide) will not hide page content positioned outside that slice** — don't assume "the menu is open and on top (z-index)" means everything underneath is visually hidden; content further from the panel's edge than its own width will still peek out. Fix by explicitly hiding the specific content that needs it (mirroring the overlay's open/closed state onto it), not by relying on stacking order alone.

Don't assume an earlier "yes" covers a later, separate Chrome tool need in the same session; ask again if it's denied.
  - `requestAnimationFrame`-driven animations throttle to near-zero when the automated tab is backgrounded/unfocused between tool calls. For clicking, prefer `find` (element-reference-based) over manual pixel-coordinate math.
