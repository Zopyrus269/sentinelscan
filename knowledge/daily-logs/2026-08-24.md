### PR #14 — correctness and production bugs (merged as `d6ef21f`)

Findings **A1–A7, C2, C3, C5, D3, D4**. 15 files, +862/−127.

- **A1** `sink.py` — the drain handler replaced gunicorn's own `SIGTERM` handler and never
  handed the signal back, so the app flushed telemetry and then kept running until Render
  force-killed it. Now captures the previous handler and chains to it (callable → call it;
  `SIG_DFL` → restore and re-raise; `SIG_IGN` → nothing to hand back to).
- **A2** `event_validation.py` — `session_id`/`trace_id`/`scan_id` arrived unchecked from the
  browser and were used verbatim as Firestore document names. One `/` failed the presence write
  and the sink dropped the whole ~100-event batch, other sessions' events included. Now
  pattern-validated and nulled out on mismatch. **Found while testing:** the first pattern still
  admitted `__name__`, which Firestore reserves for internal ids — reserved shapes are now
  rejected explicitly too.
- **A3** `firestore_sink.py` — `stats/{date}` accumulated every session id of the day in an
  unbounded array; past Firestore's 1 MB document limit *every* stats write for that day failed
  and the sink dropped *every* batch until midnight UTC. Replaced with bounded in-process
  de-duplication feeding a scalar `unique_sessions` counter (see [[DECISIONS]]).
  `get_daily_stats` falls back to the legacy array for days already written.
- **A4** `query.py` — `_flatten_events` compared the caller's raw timestamp string against each
  event's `ts`, so `...Z` and `...+00:00` (the same instant) disagreed. Both bounds now
  normalised, as `_fetch_batches` already did.
- **A5** `query.py` — `get_llm_usage` hardcoded the 7-day constant, counted a whole rollup hour
  for a mid-hour `since`, and left the window between rollup's checkpoint and now covered by
  neither branch. Range now splits on rollup's real checkpoint (`logs_meta/rollup_checkpoint`),
  with raw batches covering the edges. **D4** folded in: one shared accumulator instead of the
  same five totals added up twice.
- **A6** `rollup.py` — the checkpoint was written once at the end of a run, so a crash mid-loop
  cost the whole run and the next one re-`Increment`ed hours that had already landed. Now
  advances per chunk of `_CHECKPOINT_CHUNK_BATCHES`; `_write_hour`'s docstring no longer
  promises a guarantee the code did not give.
- **A7 + D3** `telemetry.js` — `captureError` had no count threshold, so an error storm built
  one request far larger than the server's 100-event cap and the whole payload was rejected.
  `capture`/`captureError` folded into one path with one threshold, a bounded buffer, and
  requests split by both event count and payload size.
- **C3** `seed_fake_logs.py` — a day's batches were all stamped at noon while their events
  spanned the day, so no time-range query could reach them. **The planned fix was not enough:**
  chunking only by `BATCH_SIZE` still let one batch span hours. Batches are now bounded by
  *event time* (60s) as well as size. Consequence: the seeder writes noticeably more batch
  documents per day — closer to what the live sink actually produces.
- **C5** `telemetry_routes.py` — the 64 KB cap is now checked against `Content-Length` before
  the body is buffered. **C2** — corrected/added the missing type annotations.

### PR #15 — read cost, contract, deployment, and C4 (merged as `00daf3f`)

Findings **C1, B1–B5, C4, C6–C8, D1, D2**. 9 files in the first commit, then a second commit
for C4.

- **C1 + B1** `query.py` — the ordering change described in [[DECISIONS]], plus: `_fetch_batches`
  gained a Firestore-side `limit` and a `newest_first` direction; `query_events` applies a
  24-hour default window when given neither a time bound nor a cursor; and **a cursor now
  narrows the `created_at` range to what arrived after it**. That last part is what actually
  delivers the "zero to three documents per poll" `WORKSTREAM_C.md` §10 assumes — before this,
  every poll re-read the whole window regardless of the cursor.
- **B2/B3** — `get_uptime_history` fetched up to 90 documents one at a time and
  `get_llm_usage`'s rollup branch one per hour (~550 for a 30-day range). Both now read through
  a single `get_all` round trip via a new `_read_documents` helper, with a per-document
  fallback. Billed reads are unchanged; what goes away is the sequential round trips.
- **B4** — `count_active_users` read the whole `presence/` collection unbounded; now ordered and
  capped at `_MAX_ACTIVE_SESSIONS` (500). **Tightened after review of my own change:** a cap can
  silently report a count that is really a floor, so it is now documented as saturating and logs
  a warning if it is ever hit.
- **B5** `app.py` — the sink thread and its signal handler started even with telemetry off,
  which is the production default. Gated on `pipeline.is_enabled()` (gate in `app.py`, not
  inside `ensure_started()`, so existing pipeline tests are untouched).
- **C6** `firestore.indexes.json` — all three composite indexes declared `created_at DESCENDING`
  while every query orders ascending. Corrected to `ASCENDING`, which covers both directions
  (Firestore serves a query and its exact reverse from one composite index, and C1's
  newest-first path is exactly that reverse). **Still needs console/emulator verification.**
- **C7** `app.py` — added `ProxyFix`. Behind Render's proxy `get_remote_address()` returned the
  proxy's address, so every visitor shared one rate-limit bucket.
- **C8** `render.yaml` — `SENTINELSCAN_TELEMETRY_ENABLED` declared explicitly as `"0"`. Nothing
  turns on; the switch is simply visible in the dashboard now.
- **D1** deleted the dead `_daterange` helper; **D2** merged `pipeline.py`'s split `typing`
  imports.

**C4 — corrected course mid-session.** I had deferred C4 as "integration work", reasoning that
correlating the ids needed a header convention Workstream A had not yet defined. The user
pushed back and asked for it now. **They were right and I was wrong:** the convention is already
frozen in `docs/workstreams/WORKSTREAM_A.md` (`TRACE_HEADER` / `SESSION_HEADER` =
`X-SentinelScan-Trace` / `X-SentinelScan-Session`), and `app.js:144-146` has had the hook wired
since Phase 2. Two real bugs sat behind the deferral:

- `telemetry.js` never sent an `Authorization` header, so `_derive_uid()` always returned `None`
  and every event was recorded anonymous even for a signed-in user. It now sends the Firebase ID
  token via the same `window.getCurrentUserIdToken()` the rest of the app uses, cached and
  refreshed in the background so `flush()` never awaits anything (it runs on `pagehide`, where a
  promise may never settle). `sendBeacon` cannot carry headers, so unload-path events stay
  anonymous — a deliberate trade for not losing them.
- `newTraceId()` returned a fresh id and *forgot* it, while `capture()` hardcoded
  `trace_id: null`. Since `app.js` puts that returned id straight into the
  `X-SentinelScan-Trace` header, the header and the recorded events could never match — the
  click-to-backend correlation the product is built around was silently producing nothing.
  `newTraceId()` now **starts** a trace: the id is remembered and attached to every subsequent
  event. Added `getTraceId()` and `correlationHeaders()`; `app.js` needed no change.

### The one thing deliberately left undone

The ~11,700 demo events seeded into live Firestore in session 22 still carry the C3 problem.
Fixing the seeder does not repair rows already written. The user chose to **delete and reseed
during the final integration merge**, and considered and rejected doing it now, on the grounds
that Danny is not yet building against that data.

Two things must travel with that decision, both recorded in [[NEXT_TASK]]:

1. **Reseeding on top is not an option.** The daily counters use Firestore `Increment`, so a
   second run over the same dates roughly doubles every day's totals — and a stats document
   would end up holding both the legacy `session_ids` array and the new scalar counter, with
   `get_daily_stats` preferring the counter and ignoring the array. It is delete-then-reseed or
   nothing.
2. **The delete must happen before `SENTINELSCAN_TELEMETRY_ENABLED` is switched on.** While the
   flag is off, `logs/`, `presence/`, `logs_hourly/` and `logs_meta/` hold nothing but seed data
   and a blanket sweep is unambiguous. Once it is on, real events land in the same collections
   with **no top-level field distinguishing them** — `env: "dev"` lives on each event *inside*
   the batch array, not on the batch document — so a selective delete stops being possible.

Also note: now that PR #15 has landed, the existing seeded data shows nothing on the default
view, because it is all older than the new 24-hour default window. Expected, not a regression.

## Session 24 (continued) — closing the `telemetry.js` test gap

The session log above ended by flagging one gap: `telemetry.js` had gained real logic (request
chunking, trace state, a cached ID token) with **no committed tests**, because this repo has no
JS test framework. The user asked for it to be fixed rather than carried forward.

**PR #16**, merged as `9effb88`.

### What was added

- **`tests/js/telemetry.test.js`** — 25 tests across five areas: burst/chunking safety (A7), the
  two correlation ids (C4), identity (token attached, plus the signed-out / no-`auth.js` /
  token-throws cases), page-unload delivery via `sendBeacon`, and the "telemetry never throws
  into caller code" guarantee.
- **`tests/js/harness.js`** — loads the **real, unmodified** `telemetry.js` into a fresh `vm`
  context per test, faking only the browser surface it actually touches. A fresh context *per
  test* is the point: the file is an IIFE holding module-level state and registering `window`
  listeners on load, so one shared instance would leak the buffer, the current trace and the
  cached token between cases.
- **`package.json`** — one script, `test:js`. **No test framework was installed**: `node:test`
  and `node:assert` ship with Node 20+, so this costs zero dependencies.
- **`CLAUDE.md` §4** — documents both suites, so a cold session finds them and knows not to
  "helpfully" add Jest.

### Verified by mutation, not assumed

Each headline behaviour was checked by reintroducing the bug it claims to catch:

| Mutation | Result |
|---|---|
| `trace_id: currentTraceId` → `trace_id: null` (the C4 bug) | 3 tests fail |
| `chunkEvents()` removed, whole buffer sent as one request | 2 tests fail |
| count threshold removed from `push` (the original A7 bug) | 3 tests fail |

**That third run surfaced something worth keeping:** with `FLUSH_THRESHOLD` at 20, a flush can
never hold more than 20 events, so **the 100-event cap is defence-in-depth rather than a limit
reached in normal operation** — removing `chunkEvents()` leaves the count assertions passing and
only the byte-size assertion fails. The count assertion still earns its place (it would catch a
future change raising the threshold past the server's cap) but the test now says so plainly
rather than implying coverage it does not have. `MAX_BUFFER` (500) is unreachable for the same
reason.

### Gotcha worth remembering

**`node --test tests/js` does not work** — Node resolves the path as a module and fails with
`MODULE_NOT_FOUND` instead of walking the directory. The glob form is required
(`node --test "tests/js/*.test.js"`), which is why there is an npm script rather than a command
anyone is expected to remember.

file Antigravity reads for this repo (`CLAUDE.md` is Claude Code's equivalent). So this only

remote GitHub calls (`gh pr view`/`gh pr diff`) and forbids any local git state change (checkout,
switch, pull, merge, reset, stash) or file edit during that workflow, so it can never collide with
whatever Claude Code is doing in the working tree at the same moment.
