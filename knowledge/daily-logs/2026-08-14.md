### 2. Hero URL input → PlaceholdersAndVanishInput (Aceternity, not React Bits)

**New registry-access pattern discovered this session, worth remembering for any future Aceternity-sourced component:** the user gave a direct `21st.dev/r/...` URL, but per session 4's already-known gotcha, `21st.dev` registry URLs are auth-gated (`401`) both via `npx shadcn add <url>` and a plain `curl`. **New workaround found here**: Aceternity's *own* registry, `@aceternity/<component-slug>` (not the 21st.dev mirror URL), works with the ordinary `npx shadcn@latest add @aceternity/<name>` CLI command directly, no auth needed, no manual JSON-fetch workaround required — confirmed for both `placeholders-and-vanish-input` and (later, session same day) `text-generate-effect`. `components.json` now has `"@aceternity": "https://ui.aceternity.com/registry/{name}.json"` added alongside the existing `@react-bits` entry. **When a user gives a 21st.dev URL for a component, try `@aceternity/<slug>` first before falling back to the browser-read-the-rendered-page workaround from session 4** — the slug is usually the same kebab-case name as the URL's last path segment.

Integration: `PlaceholdersAndVanishInput` is a fully self-contained form (its own input + submit arrow) with no awareness of this app's existing consent-modal scan flow (`app.js`, which hard-requires real `#targetInput`/`#openConsentButton` elements by id to exist in the DOM at `DOMContentLoaded`). Rather than modify either the vendored component or `app.js`, `index.html`'s hero now has the visible mount point (`#sentinelscan-hero-input`) *plus* a `hidden`/`aria-hidden`/`tabindex="-1"` real `<input id="targetInput">` and `<button id="openConsentButton">` sitting alongside it — `main.jsx`'s `HeroScanInput` wrapper mirrors `onChange` into the hidden input's `.value` and forwards `onSubmit` into a `.click()` on the hidden button. `app.js` is completely untouched and still drives the whole downstream authorization-modal flow. Footer's "New Scan" button `onclick` updated to scroll/focus the new visible mount instead of the now-hidden legacy input.

**Bug hit and fixed — double-transform button misalignment:** the vanish input's submit arrow (`top-1/2 -translate-y-1/2` centering) sat visibly above center, and got *worse* specifically when text was typed. Root cause, confirmed via `getComputedStyle` (not guessed): this page loads **two separate Tailwind engines** — the sitewide Tailwind Play CDN (v3, JIT-scans the whole live DOM including React-rendered markup) and the react-app's own precompiled Tailwind v4 bundle. Both generate a rule for the same `-translate-y-1/2` class, but v3 emits a legacy `transform: translateY(-50%)` while v4 emits a **separate** `translate: 0 -50%` CSS property — and `transform`/`translate` are different properties that the browser composes together rather than overriding, so the button was being shifted up by *double* the intended 50%. **This is a systemic risk for any future component using the `top-1/2 + -translate-y-1/2` (or similar `scale-*`/`rotate-*`) centering pattern on this codebase specifically**, because of the dual-Tailwind-engine setup — not a one-off. Fixed narrowly, not globally: `#sentinelscan-hero-input button[type="submit"] { transform: none !important; }` in `static/css/styles.css`, cancelling only the redundant legacy `transform` and leaving the correct v4 `translate` in place. If a future component shows a similarly-doubled transform/scale/rotate, expect the same root cause and the same scoped-cancel-the-legacy-property fix pattern.

### 6. Site-wide fluid cursor (`SplashCursor`, `@react-bits/SplashCursor-JS-CSS`)

Unlike every other React Bits component fetched this session, `npx shadcn@latest add @react-bits/SplashCursor-JS-CSS` **worked on the first try** via the normal CLI (no `Unexpected token` bug this time — inconsistent with session 1-4's experience with other `@react-bits` items; don't assume the CLI bug is fixed generally, it may just be item-specific or already-patched-per-item on reactbits.dev's side). Mounted as its own independent `createRoot()` (same "own root" pattern as the background/nav-menu/intro, since it listens on `window` directly and drives its own rAF loop — no bridging needed, unlike `FloatingLines`). Root div is `position:fixed; pointer-events:none; z-index:50` full-viewport, so it never blocks clicks/typing on anything underneath — verified by typing into the hero input through the overlay.

Four rounds of iterative user feedback, in order:
1. **"Make it white, and no splash on click."** `RAINBOW_MODE={false} COLOR="#ffffff"` via existing props (no file edit needed) for color. Click-splash had no corresponding prop — **this is the point this component stopped being "used exactly as shipped" and became a locally-modified fork**: removed the `mousedown` listener registration/handler and the now-dead `clickSplat()` function from `SplashCursor.jsx` directly. Touch behavior was already fine as shipped (`touchstart` never called `clickSplat`, only `mousemove`/`touchmove` do now).
2. **"Even a tiny nudge creates a huge splat, I don't want that — only when the cursor is in full motion."** First attempt used a **hard on/off threshold** (`pointer.moved` gated on distance > constant) — this was too blunt: any move below the threshold produced *nothing* at all, which the user then rejected mid-implementation as "not what I want" before it was even fully verified. **Lesson: for this kind of "only when X" phrasing about a continuous physical quantity (speed here), default to a continuous scale, not a binary cutoff, unless the user's phrasing is unambiguously binary.**
3. **Corrected implementation**: continuous `pointer.moveIntensity` computed per move event as `clamp(distance / MOVE_FULL_INTENSITY_DISTANCE, MOVE_MIN_INTENSITY, 1)`, then the splat's dye color (not its force/radius — those already scale naturally with raw pixel delta) is multiplied by this intensity in `splatPointer()`. Small nudges now produce a dim, small-reading splat (never fully invisible, floor `0.12`); a genuine fast swipe reaches `intensity === 1`, i.e. bit-for-bit the original unscaled splat brightness. Added as new component props (`MOVE_FULL_INTENSITY_DISTANCE`, `MOVE_MIN_INTENSITY`) rather than hardcoded constants, so future tuning doesn't require touching the component internals again.
4. **"Increase brightness a bit more when in full motion."** Added a further `MOVE_FULL_INTENSITY_BOOST` prop (set to `1.4` in `main.jsx`) that fades in proportionally to `moveIntensity` itself (`boost = 1 + (BOOST-1) * intensity`) — fully applied only right at `intensity===1`, negligible at the dim floor, so slow splats stayed essentially unchanged while fast ones got visibly brighter than the original shipped brightness. All four rounds verified live via `left_click_drag`/multi-point `hover` sequences of varying distance and screenshot comparison, plus a DOM-level check (`input.value` read after typing through the overlay) confirming `pointer-events:none` doesn't block interaction.

**`SplashCursor.jsx` is therefore now a locally-forked/modified component, not a byte-for-byte vendor copy** — unlike every other component in this codebase so far. If the user ever re-runs `npx shadcn add @react-bits/SplashCursor-JS-CSS` again (e.g. to pull an upstream update), it will silently overwrite these three local changes (click-splash removal, intensity scaling, brightness boost) — flag this before ever re-fetching it.

## 6. Word-by-word typewriter animation for the scan terminal, plus a scroll-follow fix

User: the terminal was printing entire lines instantly/all at once ("large amount of text at one time"), wanted a smooth word-by-word typing animation reusing "the same spring type animation" already used on the home page's manual URL input.

- Identified the actual mechanism being referenced: `useSmoothCaret`'s `CARET_SPRING = { stiffness: 500, damping: 30, mass: 0.5 }` in `placeholders-and-vanish-input.jsx` (a `motion/react` `useSpring`-driven caret that glides between character positions as the user types) -- exported it (was previously a local `const`) so it could be reused rather than redefined.
- `ScanTerminal.jsx`: replaced instant `appendLine` with a queue (`enqueueLine`/`queueRef`/`typingRef`). Only one line "types" at a time -- a `setTimeout`-driven `tick()` reveals one additional word every interval, and a burst of events arriving in the same 500ms poll tick now queues and types sequentially rather than all appearing in one frame.
