### 2. `origin/dhanush-changes` -- bug found, fixed, opened as a PR (not merged directly)

This is a *different* branch from the old `dhanush-changes`/"Dhanush integration" work referenced in
older commit history (`9940585`, `35c930c` -- that branch was reverted and deleted previously). This
one is new: a single commit, `a3b9096` "security-changes", never merged into `main`.

Contents: `.env.example` FLASK_SECRET_KEY placeholder fix (main had a real-looking generated secret
committed there), new `.github/workflows/secret-scanning.yml` (gitleaks CI) + `.pre-commit-config.yaml`
+ `scripts/setup_security_hooks.py`, tighter rate limits (`extensions.py` 200/day->100/day,
50/hr->30/hr, plus new per-route limits on `/api/v1/auth/session` and `/api/v1/dev/bootstrap-secrets`),
removal of an insecure local JWT-fallback decode path in `auth_utils.py` (previously trusted an
unsigned client-supplied token's claims outright when `firebase_admin` wasn't installed -- now returns
503), and a rewrite of `ssrf_validator.py` to validate *all* resolved addresses for a target, not just
the first.

**Real bug found during review**: the `ssrf_validator.py` rewrite iterated `for entry in addr_info:`
but the diff had deleted the line assigning `addr_info = socket.getaddrinfo(hostname, None)`. Every
call to `is_safe_target()` would raise `NameError`. That function is called directly in
`POST /api/v1/scan` with no `try/except` around it, so **every scan submission would have 500'd** if
this branch had merged as-is. Nothing caught it because `is_safe_target()` had zero prior test
coverage.

Fixed on a new branch `fix/dhanush-security-changes` (created from `origin/dhanush-changes`, keeping
the original commit intact): restored the missing `addr_info` assignment, added
`tests/test_ssrf_validator.py` (7 tests -- safe target, loopback, private, link-local, multi-A-record
with one unsafe entry, malformed input, DNS failure), committed as a separate fix commit on top.

Opened as **PR #1**: https://github.com/Zopyrus269/sentinelscan/pull/1 -- targeting `main`, reviewers
requested (`Dannyo6`, `sbsai25`, `bhuvan-sk`). Not merged this session; that's for the team to review
and accept.

### 3. New rule: PR required for every merge to `main`, no exceptions

Added CLAUDE.md section 10 ("Git Workflow -- Pull Request Required for All Merges to `main`"): nothing
lands on `main` without an accepted PR, applies to everyone (including Claude Code and the repo admin),
no exceptions for small commits -- including this very rule change and today's knowledge-vault update,
both done on branch `chore/pr-required-for-main` rather than committed straight to `main`. See
`knowledge/DECISIONS.md`, 2026-08-20 entry, for full rationale.

Also configured **GitHub branch protection on `main`** to enforce this server-side, not just as a
documented convention (user explicitly asked for both): `required_pull_request_reviews`
(`required_approving_review_count: 1`, `dismiss_stale_reviews: true`), `enforce_admins: true` (no
bypass for the repo owner either), `allow_force_pushes: false`, `allow_deletions: false`. Applied via
`gh api -X PUT repos/Zopyrus269/sentinelscan/branches/main/protection` (no MCP tool exposes branch
protection directly; the GitHub MCP server's token also turned out not to have PR-creation scope --
`gh pr create`/`gh pr edit` were used instead for both PRs). Verified by reading the setting back.

Opened as **PR #2**: https://github.com/Zopyrus269/sentinelscan/pull/2 (CLAUDE.md rule + this log
entry + `NEXT_TASK.md`/`DECISIONS.md` updates, all on `chore/pr-required-for-main`).
