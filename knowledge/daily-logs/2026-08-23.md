### Implementation

- `scripts/seed_fake_logs.py` (new) -- generates realistic fake sessions (a standalone `ui`
  nav event, then 2-4 "Start Scan"-style actions, each an `http`/`scan`/`llm`/`agent`/`worker`
  chain sharing one `trace_id`, ~18% ending in an `error` event) across `--days` days
  (default 14) x `--sessions-per-day` (default 20). Every event fills every frozen schema
  field, `null` never omitted; `env` is always `"dev"` so seeded data stays visually
  distinguishable from real `"prod"` telemetry later. A few of "today"'s sessions are shifted
  so their last event lands within the last 1-3 minutes, so `count_active_users()`'s 5-minute
  window isn't empty the moment the demo is first opened. Reuses `FirestoreSink.write_batch()`
  for the `logs/`/`presence/`/`stats/` document shapes (zero duplicated batching/stats logic)
  and calls `rollup.run_rollup()` for real afterward for the `logs_hourly/` summaries.
  `uptime/{date}` is written directly (one `.set()` per day with plausible checks/failures
  numbers) rather than via hundreds of individual `record_uptime_probe()` calls, which would
  itself cost a meaningful chunk of the write budget for a one-time seed.
- `apps/backend/logstore/schema.py` (edited) -- additive only: `build_batch_document()` gained
  an optional `now: Optional[datetime] = None` param (defaults to real current time when
  omitted, so every existing caller/test is unaffected), letting a caller backdate a batch's
  `created_at`/`expires_at` -- necessary because `query.py`'s `_fetch_batches()` filters
  primarily on `created_at`, so a batch of 14-day-old fake events needs a matching 14-day-old
  `created_at` to ever be found by a query.
- `apps/backend/logstore/firestore_sink.py` (edited) -- additive only: `FirestoreSink.write_batch()`
  gained the same optional `now` param, threaded through to `build_batch_document()`. The one
  legitimate reuse seam: any batch producer (the live sink thread, or this seed script) can
  now say "pretend this batch was flushed at time X."

### A pre-existing bug found and fixed (unrelated to this feature)

Running the full suite for this phase surfaced 2 failures in `tests/test_logstore_query.py`
that had nothing to do with the new code -- confirmed via `git stash` that both fail
identically on the pre-Phase-4 `workstream-b-pipeline` tip:
- `test_sums_recent_raw_llm_events_into_day_buckets` seeded a batch via the test file's
  `seed_batch()` helper without an explicit `created_at`, so it silently defaulted to real
  wall-clock "now" (`build_batch_document()`'s own default) -- which matched the test's
  hardcoded `2026-08-22` event timestamps only on the day session 21 wrote the test. Once the
  real calendar rolled to `2026-08-23`, the default `created_at` fell outside the test's
  hardcoded `since`/`until` window, so `_fetch_batches()` found zero batches. Fixed by passing
  an explicit `created_at="2026-08-22T09:00:00+00:00"` to `seed_batch()`, matching the pattern
  already used by neighboring tests in the same file.
- `test_get_uptime_history_computes_percentage_and_handles_missing_days` hardcoded the string
  `"2026-08-22"` as "today", but `get_uptime_history()` computes today from the real clock.
  Fixed by computing `today = datetime.now(timezone.utc).date().isoformat()` in the test
  itself and asserting against that, instead of a hardcoded literal.

Both are the same class of bug session 16 found and fixed in `ssl_worker`/`cookie_worker`
tests: a test that silently depended on being run on the same day it was written. Committed
alongside the Phase 4 feature in `tests/test_logstore_query.py` rather than a separate PR,
since it was found while re-verifying this phase's own test run.

### Outcome: 19 findings -- 7 real bugs (3 security-relevant), 5 read-cost, 8 contract/deployment, 4 redundancy

**Full write-up: [[workstream-b-code-review-2026-08-23]]** (new file, new `knowledge/reviews/`
directory mirroring the existing `frontend-plans/` convention). Not duplicated here -- that file
is the artifact the next session works from.

The three most serious, called out inline because they are the ones that bite in production:

- **A1 -- the app stops shutting down cleanly once deployed.** `sink.py:166` installs a SIGTERM
  handler that drains the queue but never chains to the previous handler and never exits. Under
  gunicorn this *overwrites* gunicorn's own worker shutdown handler, so SIGTERM is absorbed and
  Render force-kills after the grace period -- losing exactly the queued events the drain was
  written to save.
- **A2 -- one bad client can destroy other users' logs.** The browser-supplied `session_id` is
  used unvalidated as a Firestore document ID (`event_validation.py:80` ->
  `firestore_sink.py:136`). A `/` in it makes the write throw; the sink retries 3x then drops the
  entire 100-event batch, including every other user's events in it.
- **A3 -- telemetry can permanently break itself for a day.** `stats/{date}.session_ids`
  (`firestore_sink.py:107`) grows unbounded via `ArrayUnion`. Past Firestore's 1 MB document
  ceiling every stats write for that day fails, so every batch is dropped until midnight UTC.
  Reachable organically at ~25k sessions/day, or deliberately in ~4 minutes.

Also worth flagging here because it affects data **already written to live Firestore**:
**C3 -- the seeded demo data is unreachable by time-range queries.** `seed_fake_logs.py:297`
stamps a whole day's batches with `created_at` = noon while their events span the full day;
`query.py` only tolerates a 2-minute gap (`_CREATED_AT_SKEW`). The ~14 days / 11,751 events
seeded into `sentinelscan-3f82d` in session 22 have this problem right now, so Danny's screens
would show nothing for any historical range.

### Method note worth carrying forward

Three of the findings are invisible from reading the diff alone -- they only surface by checking
the *runtime environment's* behaviour. `sink.py`'s SIGTERM handler looks correct in isolation;
it is only wrong because gunicorn's `init_signals()` provably runs before the app is imported
(checked in `.venv/Lib/site-packages/gunicorn/workers/base.py`). Same pattern for the Firestore
document-ID and 1 MB document-size rules behind A2/A3. One thing checked this way came back

`override_defaults=True` (verified against the installed 4.1.1 signature), so the telemetry
endpoint's `60/minute` correctly replaces the global `100 per day` rather than stacking with it.
