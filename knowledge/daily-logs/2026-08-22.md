### Phase 1 implementation

`apps/backend/logstore/`:
- `schema.py` -- collection constants (`logs`, `presence`, `stats`, `uptime`), TTL/retention
  constants, and `build_batch_document()`. **One design addition beyond the original spec:** each
  batch document denormalizes the `session_id`/`trace_id`/`scan_id` values present in it onto
  top-level `session_ids`/`trace_ids`/`scan_ids` arrays, with matching `array_contains` +
  `created_at` composite indexes in the new `firestore.indexes.json`. This wasn't specified in
  the original NEXT_TASK.md spec (which only said "the read API" and "composite indexes"
  generically) -- it's what makes Phase 3's `query.py` able to find "all events for this
  session/trace/scan" without either giving up the ~100-events-per-document batching (which is
  what makes the free tier viable at all) or scanning every batch in a time window.
- `sink.py` -- a background daemon thread draining a `queue.Queue`, flushing at 100 events or
  5 seconds since the first buffered event (whichever first), exponential-backoff retry on a
  failing backend, and a bounded number of retries before dropping a batch so a persistent
  outage can't wedge the thread or grow memory unboundedly. `stop(drain=True)` performs a final
  non-blocking sweep of the queue and one last flush -- this is what a `SIGTERM` handler calls,
  so Render shutting the process down doesn't lose the last few seconds of events. Built and
  tested standalone: takes any `queue.Queue`, with no dependency on Workstream A's `emit.py`
  existing yet.
- `firestore_sink.py` -- implements the sink backend: one `logs/{batch_id}` document per batch,
  `stats/{date}` counters incremented via `firestore.Increment` (grouped by date within the
  batch, so a batch spanning midnight still gets exactly the right documents touched),
  `presence/{session_id}` upserts (one per distinct session, using only its most recent event).
  Reuses `get_db()`; degrades to a clean no-op when it returns `None`, matching
  `history_store.py`'s pattern.
- `stdout_sink.py` -- local-dev sink, prints one JSON line per event.

20 new tests across `tests/test_logstore_schema.py`, `test_logstore_sink.py`,
`test_logstore_firestore_sink.py`, `test_logstore_stdout_sink.py` -- unittest.TestCase style

### Two design judgment calls resolved with the user before implementing

The frozen contract fixes `query.py`'s 10 signatures and return shapes, but not how two fields
get derived, since neither is specified by `docs/workstreams/WORKSTREAM_C.md`:

- **`get_daily_stats().unique_sessions`**: user chose to track it **at write time** --
  `firestore_sink.py`'s `_update_stats` now also `ArrayUnion`s each date's distinct session ids
  onto `stats/{date}.session_ids`, so the read side is a single cheap document read (the
  alternative -- deriving it at read time by scanning that day's raw batches -- was rejected in
  favor of not adding read-path cost to a function Danny's status board may poll).
- **`get_health_snapshot()`'s per-worker success/failure**: worker-category log events carry
  only a level and free-text message, no explicit outcome field (e.g. `ssl_worker` logs a TLS
  timeout as `warn` even though that's a valid, successful finding). User chose the simplest
  rule -- `level in {error, fatal} = failure` -- matching how `error_rate`/`llm_failure_rate`
  are computed elsewhere in the same function, over a message-keyword heuristic (brittle, not
  part of the frozen contract) or dropping the split entirely.

### Implementation

- `apps/backend/logstore/query.py` (new) -- all 10 frozen functions plus the internal,
  non-frozen `get_write_budget_status()`. Events live nested inside `logs/{batch_id}` batch
  documents (not one doc per event), so most functions query `logs` by a `created_at` range
  (widened `+/- 2min` to absorb flush-timing skew) -- narrowed by an `array_contains` filter on
  the batch's denormalized `session_ids`/`trace_ids`/`scan_ids` array when one of those is given
  -- then filter/flatten the matched batches' events in Python against the exact remaining
  filters. Cursor pagination uses `"{ts}|{event_id}"` (ISO-8601 UTC strings sort
  lexicographically). `get_llm_usage` scans raw batches directly for the last 7 days and blends
  in `logs_hourly` rollup docs for anything older, falling back to raw if a rollup for that hour
  doesn't exist yet. `get_health_snapshot` always reads the last-hour raw window (never
  rollups). `get_write_budget_status`'s no-argument ("today") call is cached in-process for 30s,
  since the ingest endpoint calls it on every request -- otherwise the write-quota guard would
  become a meaningful read-quota cost of its own.
- `apps/backend/logstore/rollup.py` (new) -- `run_rollup(now=None)`: reads a
  `logs_meta/rollup_checkpoint` document, queries `logs` batches between the checkpoint and
  `now - RAW_RETENTION_DAYS`, aggregates their events into `logs_hourly/{date}T{hour}` documents
  (per-hour counts by level/category, llm token/call/cache-hit totals, http count/duration-sum/
  error-count) via nested-map `Increment` merges (not dotted field-path strings -- confirmed
  nested maps deep-merge correctly under `set(merge=True)`, so a partial re-run of an hour never
  clobbers another level/category already recorded), then advances the checkpoint. Never
  deletes raw batches -- Firestore's existing `expires_at` TTL still does that.
