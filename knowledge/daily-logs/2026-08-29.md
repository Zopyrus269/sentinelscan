view`/`git log`, never taken on the user's word alone (one round-trip on PR #18 where the user
initially said they'd merged but hadn't yet) — before starting the next branch and before

## Session 27 — Three-way branch integration, Phase 2 (combine + cross-branch bug fixes)

### The real bug: Workstream A's events were going nowhere

`apps/backend/observability/emit.py` kept its own private queue for every backend-originated
event (HTTP requests, unhandled errors, AI agent decisions, worker logs, LLM token usage) —
and nothing drained it. Workstream A's package only ships a manual `stdout_sink.py`, never
started automatically. Meanwhile `apps/backend/logstore/sink.py`'s real background thread only
ever drained `apps.backend.logstore.pipeline`'s *separate* queue, fed solely by the browser's
own `POST /api/v1/telemetry`. **Both branches' own docstrings already described the intended
single-shared-queue design without it ever being wired that way** — `pipeline.py`'s docstring
says outright "reconciling the two into a single shared queue is integration work, once her
branch exists." Left unfixed, switching telemetry on would have meant the log site only ever
showed browser clicks/navigation, never a single backend error, AI decision, or LLM cost figure
— most of the actual value of the observability project. See [[DECISIONS]] for the full
writeup.

**Fix:** `observability/emit.py`'s `get_queue()` now delegates to
`apps.backend.logstore.pipeline.get_queue()` instead of maintaining a second queue. Verified
end-to-end, not just by inspection: a new `tests/test_observability_logstore_integration.py`
pushes a real `observability.events.build_event(...)`-produced event through an actual
`SinkThread` to a fake backend, and separately through `schema.build_batch_document`/
`FirestoreSink.write_batch` (mocked Firestore client) to confirm the schemas genuinely agree —
they do; both were built against the same frozen event schema. Also confirmed manually: ran the
app locally (`FIREBASE_SERVICE_ACCOUNT_PATH` pointed at a nonexistent path first, per the
standing rule against writing to live Firestore by accident) with
`SENTINELSCAN_TELEMETRY_ENABLED=1`/`SENTINELSCAN_TELEMETRY_STDOUT=1` and watched a real `GET /`
request's `http` event actually reach the sink and print (twice, expected — once from the
debug-print flag, once from the local dev `StdoutSink` fallback that also fired since Firebase
was deliberately off). Categories beyond `http` (agent/worker/llm) weren't separately exercised
against a live scan this session — covered instead by the automated test, since every one of
Workstream A's producers shares the same `emit()` entry point that was just proven live for
`http`.

### The one real merge conflict: `apps/backend/app.py`

Predicted before merging (both branches independently edit the code right after
`limiter.init_app(app)`) and confirmed exactly there — no other file overlaps between any two
branches. Hand-merged: `observability.init_app(app)` now runs before
`pipeline.ensure_started()`, so the sink is ready to drain by the time the app can start
emitting into the now-shared queue.

### A second, smaller bug the merge itself surfaced

`tests/test_telemetry_routes.py` builds the real app with telemetry enabled, so — now that
Workstream A's request hooks are actually wired in — every test's own `self.client.post(...)`
to the endpoint under test also generates a backend-sourced `http` event into the same shared
queue the tests inspect, breaking exact-count/set assertions. Fixed by filtering
`_drain_queue()` on `source == "frontend"` (the browser-ingest path's own, permanent tag), which
scopes these tests back to what they're actually testing without asserting anything about the
separately-tested observability hooks.
