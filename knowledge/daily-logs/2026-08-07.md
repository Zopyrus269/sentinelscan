## Root cause found: package-level MCP roots override, not a config bug (same day)

**What & why:** A fresh session was restarted per the previous entry's instruction and re-ran the three verification checks. They still failed exactly as before: `list_allowed_directories` returned the repo root, and `docs/PRD.md` read through `knowledge-vault` succeeded. Since `.mcp.json` was confirmed correct and committed, and the previous entry had already ruled out a stale-process explanation once, the investigation moved to the MCP server package itself rather than repo config.

**What was found (real root cause):** `@modelcontextprotocol/server-filesystem` (unpinned via `npx -y`, resolving to the latest published version, `2026.7.10`) implements the MCP **roots protocol**. In `dist/index.js`, `server.server.oninitialized` checks `clientCapabilities?.roots`; if the connecting client advertises roots support, the server calls `listRoots()` and **overwrites** its own `allowedDirectories` (originally set from the CLI arg) with whatever directory list the client reports — `allowedDirectories = [...validatedRootDirs]`, a full replace, not a merge. Claude Code advertises roots support and reports its own workspace root (the whole repo) back to the server, so the `knowledge/`-scoped CLI argument in `.mcp.json` was being silently discarded post-handshake on every connection, restart included. This explains why the bug survived both the absolute-path fix (`34fac14`) and a full session restart — neither touches the client's roots advertisement, which is what actually wins.

**Version audit performed:** Downloaded and inspected the `dist/index.js` source of 8 published versions directly (via `npx -y server-filesystem@<version>` then grepping the resolved npm cache, not changelogs/registry metadata). Roots-override code is present in `2025.8.21`, `2025.11.25`, `2025.12.18`, `2026.1.14`, and `2026.7.10`. It is **absent** in `2025.1.14`, `2025.3.28`, and `2025.7.1` — confirmed by full-file audit of `2025.7.1`, where `allowedDirectories` is a `const` never reassigned after startup and access control is purely `isPathWithinAllowedDirectories` against the CLI-supplied directory list. The roots feature was introduced sometime between `2025.7.1` and `2025.8.21`.

**Fix applied:** Pinned `.mcp.json`'s `knowledge-vault` server to `@modelcontextprotocol/server-filesystem@2025.7.1` (last confirmed roots-free release), keeping the same absolute path (`C:/Dev/SentinelScan-Project/knowledge`) from the prior fix. Pinning (rather than just picking a version once) also prevents unpinned `-y` resolution from silently drifting onto a newer roots-capable release in the future.

**Files changed:** `.mcp.json` (`args` updated to pin the exact version). No application code touched. `README.md`, `LICENSE.md`, `headless_auth_test.py` left untouched per instruction.

**Testing performed:** Static source audit only in this pass (grepped each version's resolved `dist/index.js` for the roots-handshake code path; read the full `2025.7.1` source end-to-end to confirm no alternate override path exists). Live in-session verification (`list_allowed_directories` → `knowledge/` only; `NEXT_TASK.md` read succeeds; `docs/PRD.md` read denied) is **not yet done** — deliberately deferred, since two other Claude Code sessions were found to be concurrently running against this same project with their own `knowledge-vault` subprocess pairs, and killing them mid-session to force a reconnect (as tried previously) doesn't work anyway and risks disrupting the other session. User chose to restart this session themselves instead.

**Current project state:** Root cause identified with source-level evidence (not inference); fix committed to `.mcp.json` on disk; live verification outstanding pending user's manual session restart.

**Recommended next steps:** After restarting, re-run the three checks. If `2025.7.1` proves too old in some other way (missing a tool the vault workflow relies on — unlikely, since only `read`/`write`/`edit`/`list`/`search` primitives are used, all present since early versions), the next safe candidate is `2025.3.28`, also confirmed roots-free.

## Third layer found: daemon caches MCP subprocess across forked/resumed sessions (same day)

**What & why:** User asked to apply the confirmed `2025.7.1` pin, reconnect via a fresh session, and verify. `.mcp.json` was already correctly pinned from the prior entry. A "fresh" session was used to re-run `list_allowed_directories` — it still returned the repo root.

**What was found:** Process-ancestry tracing (walking `ParentProcessId` from a tool call's own PID up to the owning `claude.exe`) showed this environment's Claude Code process tree is: a persistent daemon (`claude.exe daemon run --origin transient`) → a `--fork-session --resume <transcript>.jsonl` process → the actual session. "Restarting" in this setup forks/resumes against the daemon rather than cold-starting a new process, and the daemon was still handing this forked session the **same MCP subprocess instance** spawned before the `.mcp.json` pin was written (created 5:28 PM, well before the fix) — confirmed by its command line showing the old unpinned `-y @modelcontextprotocol/server-filesystem` invocation, not `@2025.7.1`. So the two fixes already committed (absolute path, then version pin) were both correct on disk but never actually got exercised by a live process.

**Action taken:** Traced this specific session's own private subprocess tree via full ancestry walk (to avoid the mistake of guessing by process list alone, which showed 4 filesystem-server processes belonging to at least 2 different sessions). Killed only the confirmed-own tree (`taskkill /PID <root> /T /F`). This cleanly disconnected `knowledge-vault` for this session (confirmed via `ToolSearch` returning no matching tools) but, consistent with the earlier documented finding, **did not trigger a respawn** — the client only spawns MCP subprocesses once per process lifetime, and a fork/resume inherits the daemon's existing subprocess rather than requesting a new one.

**Decision:** Do not keep attempting mid-session kills — it's a proven dead end across two separate attempts now. User will perform a genuine cold restart (full exit and relaunch of the Claude Code application/CLI, not a resume/fork) so a brand-new process actually re-reads `.mcp.json`.

**Files changed:** None this pass — `.mcp.json` was already correct. `knowledge/NEXT_TASK.md` overwritten to describe this third layer and warn future sessions off the same dead-end approach. `README.md`, `LICENSE.md`, `headless_auth_test.py` untouched.

**Testing performed:** Process-ancestry walk (`Get-CimInstance Win32_Process`, following `ParentProcessId` chains) to positively identify this session's own subprocess tree before killing anything; confirmed the kill via `ToolSearch` showing `knowledge-vault` tools gone; confirmed no auto-respawn by re-querying `ToolSearch` immediately after.

**Current project state:** Fix is correct and complete on disk (`.mcp.json` pinned to `2025.7.1`, absolute path). Live verification still blocked — now understood to require a genuine cold restart, not merely "starting a new session" in whatever form this environment's daemon treats as a restart.

**Recommended next steps:** After a full cold restart (verify by checking that the new session's `knowledge-vault` subprocess has a recent `CreationDate` and `@2025.7.1` in its command line before trusting `list_allowed_directories` output), re-run the three verification checks and close out [[NEXT_TASK]]. If a cold restart *still* doesn't produce a fresh subprocess, the daemon process itself (`claude.exe daemon run --origin transient`) is the next suspect — but killing a daemon shared by multiple sessions is higher blast radius and should be confirmed with the user first.
