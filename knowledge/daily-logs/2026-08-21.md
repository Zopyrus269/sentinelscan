### Part B -- Root-caused and fixed the 5 failing tests (two distinct causes, not one)

**B1: `test_cookie_worker`, `test_headers_worker`, `test_sitemap_worker` (x2) -- test isolation
bug.** `cookie_worker.py`, `headers_worker.py`, and `sitemap_worker.py` all gained a Playwright
browser fallback (`apps.backend.utils.browser_fetcher.fetch_with_browser`) at some point after
these tests were written: on `requests.Timeout`/`ConnectionError`, each worker now retries via
headless browser instead of failing immediately, returning `{"error": ...}` only if the fallback
*also* fails. The tests mocked `requests.get` but never `fetch_with_browser`, and `setUp()` uses a
real, live target (`https://example.com`) -- so under real network access the un-mocked fallback
silently succeeded against the actual internet (or, for sitemap, got real HTML back that failed
XML parsing), masking the structured error the tests were meant to verify. Fixed by mocking
`fetch_with_browser` to also raise, so the tests genuinely exercise "both primary and fallback
failed".

Used `graphify affected "fetch_with_browser"` to find every caller -- this is what surfaced that
`ddos_worker.py` and `robots_worker.py` also call it, which a per-file grep sweep of just the three
known-failing workers would have missed entirely. Checked both: no active bug in either.
`ddos_worker` has no timeout/connection-error test at all; `robots_worker`'s existing
`test_robots_worker_request_exception` only exercises the generic `RequestException` branch
(`robots_worker.py:119`), never the `Timeout`/`ConnectionError` branch (`robots_worker.py:80`)
that triggers the fallback -- it dodges the trap by accident, not by design. Nothing fixed there,
just flagged in the commit message so a future test for either worker doesn't reintroduce the same
bug by copying the existing pattern.

**B2: `test_ssl_worker::test_socket_timeout` -- stale assertion, not a worker bug.**
`ssl_worker.py`'s `perform_ssl_inspection` already (intentionally) treats a TLS handshake
`socket.timeout`/`TimeoutError` as a **successful** scan result -- `certificate_verified=False`,
`verification_error="Target dropped connection (no SSL cert retrieved)"` -- matching the same
explicitly-commented philosophy ("THIS IS SECURITY EVIDENCE. Do NOT return worker failure here.")
already applied a few lines earlier to `ssl.SSLCertVerificationError`. The test still asserted
`status == "error"`, which no longer matched. Confirmed with user before touching anything (this
changes test semantics, not a pure bug fix): update the test, not the worker -- the worker's
behavior is intentional and correct. Updated the assertion to check for the success-with-evidence
shape instead.

## Session 17 -- Found and fixed a real Graphify hygiene bug: redundant committed backup snapshots

While reviewing PR #7 (session 16's vault+graph update), user noticed it added **over 30,000
lines** and asked directly whether graph regeneration was a full rebuild or an incremental append,
and whether this was burning tokens/repo size unnecessarily. Investigated rather than assuming --
`git log --stat` on `graphify-out/` across both PR #4 (session 15) and PR #7 (session 16) showed
the pattern was identical both times: a small legitimate `graph.json` diff (9,038 lines this
session; full-file rewrite is expected since `--force` does a real full re-scan, not incremental --
`graphify update` is deliberately never used here, see CLAUDE.md section 11) plus a **~30K-line
duplicate** written into a new `graphify-out/YYYY-MM-DD/` folder every single time.

Traced the duplicate to `graphify/export.py`'s `backup_if_protected()` (in the installed package at
`~/.local` via `uv tool`): it auto-snapshots the whole graph into a dated subfolder before any
overwrite of a graph with real LLM-assigned community labels (ours qualifies, via the `claude-cli`
labeling backend) -- and its own docstring says `Set GRAPHIFY_NO_BACKUP=1 to disable`. Neither
session 15 nor session 16 knew about or used that flag, so both committed the resulting duplicate
straight into git as part of "`graphify-out/` is committed" without questioning it.

**User gave one-time explicit authorization to push this fix directly to `main`, bypassing the
PR-required rule.** Checked first whether that was even possible: `main`'s branch protection has
`enforce_admins: true` and an active required-PR-review policy, so a direct push would be rejected
by GitHub regardless of authorization -- would have required temporarily disabling branch
protection first, which is a materially bigger action than "just push this". Surfaced that
distinction to the user via a clarifying question rather than assuming; user chose the normal
branch+PR flow instead, protection left untouched throughout.

### Fix
- Deleted the two already-committed dated folders (`graphify-out/2026-08-20/`,
  `graphify-out/2026-08-21/`, ~67,600 lines removed net).
- Added a `.gitignore` pattern (`graphify-out/[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]/`) as a
  backstop in case a future regeneration forgets the env var.
- `CLAUDE.md` section 11 now documents `GRAPHIFY_NO_BACKUP=1` as a required part of the
  `extract`/`label` commands, with the rationale (git already versions `graph.json` on every
  commit; the graphify-internal snapshot is pure redundancy once committed).

## Session 18 -- Planned the observability/logging project and wrote the three-way handoff package

User asked for a logging architecture for the whole project, surfaced on a **second, separate,
developer-only website** modelled on status.claude.com / status.gemini.google.com. The driving
problem, in the user's own framing: when a user reports a vague bug, the team currently has to
re-read code and guess, burning time and tokens. They want to open a log site instead, find that
person's visit, and read what actually happened.

Confirmed the gap first rather than assuming it: `logging.getLogger(__name__)` is called in 13
backend modules but **no handler is ever configured anywhere**, so almost all of that output goes
nowhere. Nothing is captured from the browser at all. Render's free tier keeps no durable logs.

### The six acceptance criteria (user's words, condensed)

1. Whether the main website is up and running
2. Number of active users on the website
3. Each user's activity stored with timestamps
4. The internal work happening behind a button click, which the user cannot see
5. Gemini API token usage
6. Overall website health

Plus one hard constraint, stated explicitly: **the log site must not affect the speed of the
main website** -- it is "a window to it", not a component of it.

### Design decisions (rationale in [[DECISIONS]])

Presented four choices to the user in plain, non-technical terms after they asked twice for
simpler explanations; they picked deliberately, not by default:

- **Firestore, not Postgres.** Already wired (`firebase_client.py`, `history_store.py`), free,
  no new credentials. Render deletes free Postgres instances after 30 days, which disqualified
  the better query engine. Cost of the choice: batching is mandatory, not optional.
- **Written timeline, not session replay.** rrweb was offered and rejected -- bundle weight,
  storage volume, and the masking burden of never recording typed text.
- **Second Render service from this same repo**, not a subpath on the main app. The user wanted
  two genuinely separate websites. Accepted cost: free-tier services sleep after 15 min, so the
  log site cold-starts in ~30-50s. Mitigated architecturally: **ingestion lives on the main
  service**, so nothing is lost while the log site sleeps.
- **Frontend deliberately plain.** User was explicit that the frontend is not a big concern --
  "a basic setup like the Claude Code status website will do" -- and that more effort belongs on
  making the backend work properly. So the log site is vanilla HTML/JS + Tailwind CDN, no build
  step, and the workload was weighted toward backend depth in all three streams.

### The architecture, in one paragraph

The browser generates a `session_id` (per tab session) and a fresh `trace_id` per user action,
sending both as `X-SentinelScan-Session` / `X-SentinelScan-Trace` headers on every fetch. Flask
reads them into `g`; every backend event inherits them. **The click event and every piece of
backend work it caused therefore share one `trace_id`** -- which is the entire mechanism behind
requirement 4. Events go into a bounded in-memory queue (non-blocking, drops on overflow); a
background thread batches ~100 of them into one Firestore document. The log site reads Firestore
directly and never touches the main app, except one uptime probe.

### R2 -- the decision that actually makes the merge safe

Once the user confirmed **they** would be integrating, the biggest available merge-safety win
became obvious: **no workstream edits any existing file at all.** Every edit to `app.py`,
`gemini_client.py`, `orchestrator.py`, `scan_routes.py` and `render.yaml` moves to the
integrator. A and C each ship an `INTEGRATION.md` describing their required edits with
copy-paste-ready snippets instead of making them. Those five files were the only real collision
surface across three branches; removing them removes the collision.

An earlier draft had Workstream A editing all four backend files (it was assigned to the user at
the time). Reassigning A to Sanjana is what exposed the problem.

### Two traps recorded now so integration does not rediscover them

- **`contextvars` do not cross `threading.Thread` boundaries.** `_run_scan_background`
  (`apps/backend/routes/scan_routes.py:81`) runs every scan on a fresh thread. Without an
  explicit snapshot/restore, all scan events lose their `trace_id` and requirement 4 renders an
  empty result -- **no exception, no failing test, just a silently empty feature**. Called out
  prominently in Sanjana's handoff as one of two "hard problems"; verify it holds at integration.
- **Cursor polling on the log site is mandatory.** Three developers idling with the site open,
  refreshing every 20s over a 50-doc window, is ~108,000 reads/day against a 50,000/day free
  limit -- and it would take the main app's history feature down with it, since they share the
  quota. Cursor polling at 30s intervals brings it to ~2,900/day. Documented with the arithmetic
  in Danny's handoff so it reads as a constraint rather than a style preference.
