### Bugs hit and fixed this session

1. **`npx shadcn@latest add @react-bits/FloatingLines-JS-CSS` fails with `Unexpected token (1:0)`.** This is a bug in the shadcn CLI's item-resolution step itself (reproduced on both `shadcn@latest` and the CLI's own suggested fallback `shadcn@4.16.0`; plain `shadcn add button` works fine, so it's specific to resolving react-bits registry items, not our `components.json`/registry config). Worked around by fetching the registry item's JSON directly (`https://reactbits.dev/r/FloatingLines-JS-CSS.json`, valid, reachable) and placing the two files (`FloatingLines.jsx`, `FloatingLines.css`) plus the `three` dependency exactly as the CLI would have. **If this CLI bug still reproduces on the next component, don't waste time re-diagnosing — go straight to the manual fetch-and-place workaround.**
2. **`ReferenceError: process is not defined` at runtime.** React's dev-mode code paths reference `process.env.NODE_ENV`, which isn't defined in a browser bundle unless Vite is told to replace it. Fixed by adding `define: { 'process.env.NODE_ENV': JSON.stringify('production') }` to `vite.config.js` — also shrank the bundle (674KB vs 1063KB) by dead-code-eliminating React's dev-only branches.
3. **Background invisible except in a thin gap below the footer.** The existing 9 pages set an opaque `bg-background` (Tailwind CDN utility, generated per-page from an inline `tailwind.config` script) directly on `<body>`, and `bg-background`/section-band colors on `<footer>` and one `index.html` section — these painted over the fixed `z-index:-1` React background entirely. **User explicitly approved this deviation from "shipped as-is"**: made `body`/`footer` backgrounds transparent (`body, footer { background: transparent !important; }` in the react-app's own `index.css`, `!important` needed because Tailwind's CDN script injects its utility CSS after ours) plus one one-off edit removing `bg-surface-container-lowest` from the "How SentinelScan Works" section in `index.html`. Card/dialog/nav surfaces (`bg-surface`, the header, dropdowns, modals) were deliberately left alone for legibility — this matches the site's own existing pattern (most inner pages are literal "cards floating on the body background," so only the body-level backdrop needed to change).
4. **No cursor-reactive hover animation despite the component code being correct.** `FloatingLines` attaches `pointermove`/`pointerleave` listeners to its own `<canvas>` — correct for the React Bits demo where it's a normal top-level element, but as a `z-index:-1` full-page background the browser always routes real mouse events to whatever's visually on top, so the canvas structurally never receives them, regardless of the component's own code. **User caught this by comparing directly against reactbits.dev and asked for a fix, "use the component as shipped."** Fixed with a bridge in our own `main.jsx` (not the shipped component files): a `window`-level `pointermove` listener that forwards real cursor coordinates into the canvas via `canvas.dispatchEvent(new PointerEvent(...))` (dispatchEvent invokes target listeners directly, bypassing hit-testing). Hit a self-inflicted infinite loop on the first attempt — forwarded events had `bubbles: true`, so they bubbled back up to the same `window` listener and re-triggered forwarding forever (`Maximum call stack size exceeded`); fixed by setting `bubbles: false` (the canvas doesn't need the event to propagate further). Verified with a temporary console counter that hover moves map 1:1 to canvas events with no runaway loop, plus visual confirmation that the lines bend and the background parallax-shifts with the cursor.

## Session 2: first-visit intro preloader (double-stairs reveal)

User asked to integrate a second component, **Skiper UI's `skiper10`** ("Double Stairs Preloader," `npx shadcn add @skiper-ui/skiper10`), as a one-time intro animation: plays once per browser tab on first load, never on refresh, then reveals the site.

### Why it's hand-built, not the shipped component

`skiper10` turned out to be a **paid Skiper UI Pro component** — its registry endpoint (`https://skiper-ui.com/r/skiper10.json`) returns `401 {"error":"Missing license key..."}` without a purchased license. User chose (via `AskUserQuestion`) to have it rebuilt from scratch rather than buy a license or substitute a free alternative. This is a one-off exception to the workstream's normal "use React Bits components as shipped" pattern — `skiper10` isn't a React Bits/`@react-bits` registry item at all, it's a different (Skiper UI) paid registry, so the established React Bits workflow/gotchas in this file don't apply to it.

Also could not use Skiper UI's own proprietary self-hosted display font (found via their site's `@font-face customFont` rule, a licensed brand asset) — used `Inter`/700 weight instead, matching this project's own existing `display` typography scale already defined in each static HTML page's inline Tailwind config (`fontSize.display: ["48px", {fontWeight:"700", ...}]`), so the wordmark reads as SentinelScan's own type system rather than a mismatched borrowed font.

### What it does

`apps/frontend/react-app/src/components/IntroPreloader/IntroPreloader.jsx` (new) + orchestration in `main.jsx`:

1. **Text reveal** — "SentinelScan" (Inter/700, `clamp(2rem,6vw,4.5rem)` so it scales but never dominates the screen) fades/settles in on solid black, holds ~2.2s, then fades back into darkness. ~2.35s total.
2. **Double-stairs reveal** — 8 full-height columns, each split top/bottom, slide off-screen in opposite directions with a `100ms` per-column stagger and `expo-out` easing (`[0.16,1,0.3,1]`), so the leading edge reads as a diagonal staircase uncovering the real page. No entrance-stairs animation — the overlay starts already fully covering (matches the real component's behavior, confirmed by inspecting `skiper-ui.com`'s own demo page mid-animation).
3. Gated by `sessionStorage.sentinelscan_intro_seen` — plays once per tab, skipped on any same-tab refresh/nav. A synchronous inline `<script>` in every page's `<head>` (same pattern as the existing dark-mode FOUC-prevention script) hides `<html>` before first paint if the flag is absent, so there's zero flash of page content before the preloader covers the screen; a `useLayoutEffect` in the intro's own root un-hides it in the same paint frame once the overlay is committed.

All timing/sizing went through two rounds of user feedback (too-fast/too-big initially, iterated to the current ~5.7s-ish full sequence with a genuine multi-second hold) — current constants live in `IntroPreloader.jsx`'s `TIMING` export; treat those as tuned/settled, not placeholders.

### Bug hit and fixed: intro finishing looked like a page reload

**Symptom:** right as the stairs finished opening, the `FloatingLines` WebGL background visibly "restarted" — read to the user as the page reloading.

**Root cause, confirmed by instrumenting both components with mount/unmount `console.log`s and reading them back via Chrome console (not guessed):** `FloatingLines` was mounted as an unconditional sibling of the conditionally-rendered `<Intro/>` inside one shared React root/fragment (`{showIntro && <Intro/>}<SiteBackground/>`). Despite `SiteBackground` occupying the same array position across renders (which should be reconciliation-stable per React's own docs), it empirically unmounted and remounted at the exact millisecond `showIntro` flipped to `false` — resetting the Three.js scene's `Clock` and restarting the shader animation from `t=0`. Exact mechanism inside React's reconciler wasn't chased further once the fix below was confirmed to eliminate it cleanly; if this class of bug resurfaces elsewhere in this tree, don't assume positional-sibling reconciliation is safe — verify empirically with the same mount/unmount logging technique rather than trusting the general rule.

**Fix:** split into **two fully independent `createRoot()` calls** in `main.jsx` instead of one shared tree — `SiteBackground` mounts on its own root immediately and is never touched again by anything intro-related; the intro mounts on a separate root only when the session flag is absent, and calls `introRoot.unmount()` + removes its own mount-point `<div>` on completion. This makes cross-remounting structurally impossible rather than dependent on reconciler behavior. Re-verified with the same mount/unmount logging: exactly one `FloatingLines` mount log for the entire session, no unmount/remount pair, background is already several seconds into its animation by the time the stairs open.

### 2. Hero ShutterText: from "paste the vendored component" to a purpose-built extraction

User asked to add 21st.dev's **"Hero Shutter Text"** (`daiv09/hero-shutter-text`) in place of the static "AI-Powered Website Security Scanner" `<h1>`. This went through several corrections worth recording as the final state, not just the end diff:

1. **21st.dev registry is gated**, unlike the public React Bits registry — `npx shadcn add <url>` failed with `401`/`Authentication required`, and a plain `curl` to the same URL also 403'd (`X-Api-Key`/session-gated). User was already signed in via the browser, so the component source was read directly off the rendered page (`get_page_text`) instead — same "manual fetch when the CLI can't" pattern as the React Bits CLI-bug workaround, but for a different reason (auth, not a CLI bug).
2. **First attempt pasted the vendored component verbatim** (`src/components/ui/hero-shutter-text.tsx`, kept as `.tsx` specifically to leave its TS prop-typing untouched) and mounted it with default props (text "IMMERSE", the demo's own grid background, corner accents, and click-to-re-shutter button). **User rejected this as "very bad implementation"** — an unmodified demo component isn't the same thing as "this animation on our own heading text."
3. **Rebuilt as a purpose-extracted component**, `src/components/ShutterText/ShutterText.jsx`: kept the per-character shutter-slice mechanics byte-for-byte (same `delay: i*0.04+...`, `duration`, `easing`, all three `clipPath` slice bands/colors), dropped everything that was demo scaffolding rather than animation (grid background, corner accents, re-shutter button + its remount-on-click state), and drove it with the real heading text. Deleted the vendored `.tsx` file entirely — nothing from it ships anymore.
4. **Layout fixes on the extracted version**, three more rounds of user feedback:
   - "Scanner" was wrapping mid-word onto a second line — the per-character `flex flex-wrap` layout plus a fixed-rem font clamp let the phrase exceed the container width. Switched to `flex-nowrap` and changed the font-size to a pure viewport-scaled value (`min(3.1vw,3rem)`) so the phrase's total width stays proportional to the viewport at every breakpoint instead of wrapping.
   - The "y" in "Security" had its descender leg clipped. Root cause: each character's wrapper needs `overflow` clipping on the x-axis only (to contain the slice layers' horizontal sweep so it doesn't bleed into neighboring letters) but the wrapper's line-height-1 box is tighter than this font's descender depth. A naive `overflow-x-hidden overflow-y-visible` did **not** fix it — per the CSS Overflow spec, pairing `hidden` on one axis with `visible` on the other silently promotes the `visible` one to `auto`, which still passively clips (no scrollbar ever appears to reveal it). Fixed by using `overflow-x-clip` instead of `-hidden`: `clip` is the one value that doesn't trigger that pairing rule, so `overflow-y` actually resolves to `visible` (confirmed via `getComputedStyle`, not just visually). **Worth remembering for any future single-axis-clip need in this codebase.**
5. **Reveal timing, two iterations:**
   - First cut mounted `ShutterText` immediately at page load, ungated. Since the intro preloader visually covers the whole page for ~6.4s on a first visit, the animation finished *underneath* the intro and visitors only ever saw the settled final text once the intro uncovered it.
   - Fixed by gating a `start` prop on the component: while `start=false`, every span's `animate` target collapses to its own `initial` values (held, inert) instead of unmounting/remounting — cleaner than conditional mounting since it doesn't fight `AnimatePresence`/re-triggering. `main.jsx` flips `start` via a `sentinelscan:intro-reveal-start` custom event.
   - **User's second round of feedback**: gating on the intro's full completion (`onDone`) still felt like the animation played "after" the reveal rather than "as" the reveal. Split the intro's single `onDone` timeout into two: `onRevealStart` (fires at the `open` stage's own `setTimeout`, i.e. the instant the stairs *begin* opening) and `onDone` (unchanged, fires at full completion, still handles `sessionStorage`/unmount cleanup). The hero animation is now gated on `onRevealStart`, so it plays in lockstep with the curtain opening rather than after — the "site booted up instantly" effect the user asked for. Returning visitors within the same tab session (intro already seen) still get it immediately on mount, no gating.

**Claude-in-Chrome caveat hit hard this session, worth restating strongly:** `document.hidden`/`document.visibilityState` flapped unpredictably between automated tool calls in this session, well beyond the already-documented rAF-throttling note — clicking into a tab did not reliably yield `document.hidden === false` on the next check, and having more than one MCP tab open at once made it worse (a second tab silently backgrounds the first). Since framer-motion's whole animation engine (not just paint) is driven by `requestAnimationFrame`, a hidden document doesn't just render a stale frame, it fully pauses animation *progress* — even logically-correct state changes (React state flips, style targets change) sit inert until the tab is next visible. When verifying animation-timing logic here, prefer checking things that don't depend on live rAF progress (event-listener wiring, computed `overflow`/style values, DOM structure) over trying to catch a live mid-animation frame; if a live frame is needed, keep exactly one tab open and expect to retry.
